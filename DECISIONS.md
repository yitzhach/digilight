# Decisions

Anything BUILD.md leaves open or gets wrong: the simplest option that keeps its promises, logged here.

- **D-001 (Phase 0). Only `core` and `web` are scaffolded.** `gl`, `mcp`, `e2e/` and the other files in §4 are created in the phase that first needs them (§3: no file the brief does not ask for).
- **D-002. `zod` and `@preact/signals` are not installed yet.** Both are in the §4 stack; they are added when code first uses them (`zod` in Phase 1, signals in Phase 3).
- **D-003. Versions.** TypeScript 5.9 (§4 says 5; 7.x exists), Vite 7, Vitest 3, Preact 10, pnpm 10.28 (`packageManager`), Node 20+ (CI uses 22). No `wrangler` dependency: Workers Builds provides it and Phase 0 does not deploy.
- **D-004. Package names are `core` and `web`**, so `pnpm --filter web dev` works as the gate says.
- **D-005. Copied files are verbatim.** `bench/bakeoff/*.py`, `docs/bakeoff.md` and `fixtures/README.md` still name v1 paths (`testdata/photos`, `samples/`, `tools/bakeoff`, `docs/v2`). `common.py` builds paths from `REPO + '/testdata/photos/'` and `'/samples/dsc8382/'`; they must point at `fixtures/` and `fixtures/dsc8382/` before the scripts run (Phase 5 or 10). In `fixtures/`, `samples/painting.jpg` is `fixtures/painting.jpg` and `samples/dsc8382/` is `fixtures/dsc8382/`.
- **D-006. `wrangler.jsonc` `compatibility_date`** is the date of Phase 0 (2026-11-11).
- **D-007 (Phase 1). Dependencies.** `zod` 4 (core: the schema). Dev only, for tests and scripts: `jpeg-js` (decodes the fixture JPEGs and encodes the contact sheet; pure JavaScript, no native build) and `@types/node`. `core/tsconfig.json` covers `src/` with no Node or DOM types, so `src/` stays pure; `tsconfig.node.json` covers `test/` and `scripts/`.
- **D-008. Scripts run on Node's own TypeScript** (type stripping, Node 22.18+): `node scripts/x.ts`, no `tsx`. Imports carry `.ts` extensions (`allowImportingTsExtensions`, `erasableSyntaxOnly`).
- **D-009. Light colour table.** v1's Planckian spline is valid from 1667 K, so 1500 and 1600 K equal 1667 K. Display P3 uses the standard XYZ to Display P3 (D65) matrix (v1 had sRGB only). 6500 K is set to exactly (1, 1, 1).
- **D-010. Dramatic look: lamp brightness 1.1 to 1.0.** With §5 exactly, 1.1 gives `kappa` 0.66 on the lintel (the bakeoff mock used a different kelvin curve and a 256 px thumbnail: 0.73); 1.0 gives 0.72. BUILD.md §6 table updated. Measured: every look `kappa` 1 on the door; on the lintel gallery 0.95, raking-top 0.96, dramatic 0.72, the rest 1.
- **D-011. Not rendered yet:** relief (`relief.mode` is treated as off until Phase 4), sheen (a surface property: only with relief on), finish (Phase 6). The settings are in the schema and validated.
- **D-012. Defaults §6 leaves open:** sun `azimuth` 135 (upper left), `elevation` 30; `aim` range −2 to 3 like `pos`; the schema default `pos` is the "+ Add light" position. Unknown keys are rejected; missing settings get defaults.
- **D-013. `render(photo, doc, {width, region, kappa})`**: `kappa` is optional, so callers that split rows across workers compute the guard once (`guardKappa`). Returns `{data, width, height}` for the region. A photo whose long side is 512 or less is its own guard thumbnail (no upscaling).
- **D-014. `open(photo)` takes the file's SHA-256 from the caller** (the app or command line hashes the file); `core` does no hashing.
- **D-015. Commands not built in Phase 1:** `setRelief`, `measureRelief` (Phases 4, 5), `export` (Phase 3, it needs image encoding). `render` returns `{image, metrics}`. New lights are `light-N`, the smallest unused N.
- **D-016. Encode** starts its search from a 4096-bucket index of the threshold table: the same answer as the plain binary search (tested on every code), about three times faster.
- **D-017. Look strength mixes as `a(1 - s) + b s`**, so strength 1 gives the table's numbers exactly and 0 gives neutral exactly.
- **D-018. Metrics** compare shares (blown, crushed by display luma) with the photo at the same size and region; warnings when new blown is over 0.5% (the guard's limit), new crushed over 0.15% (v1's limit), or `kappa` < 1. v1's texture and thirds numbers are dropped. The guard judges at 512 px, so a render at another size can show a little over 0.5% with `kappa` 1.
- **D-019. Review rounds replace the contact sheet** (Isaac asked for an easy way to mark pictures and type or speak notes): `core/scripts/review.ts` + `review-page.html` write a page that saves each note to the artifact's database, where the next session reads it. Rebuilt from v1's lighting-round page (`tools/looks/review-template.html`).
- **D-020. Looks retuned from Isaac's round 1 notes** (too warm, highlights blown, spotlight too hard, window and daylight too subtle): lamps lower and cooler, room light higher and cooler, spotlight wider and softer, window closer with full falloff, daylight cooler. BUILD.md §6 table updated, goldens regenerated. On the door, gallery's near-white share (display luma >= 235) went from 8.1% to 2.7% (photo 0.07%). The lintel's white plaster still goes near-white under most looks; round 2 asks whether the guard should count from 240 (`guardKappa(photo, doc, at)` takes the level for comparison only; §5.7 still says 250). Raking looks stay subtle until Texture (Phase 4), as §6 says.
- **D-021. Round 2: the whites guard stays at 250 (§5.7 unchanged).** Isaac: the stricter version goes grey and flat. Blowouts were local: a lamp close to a corner or edge lights it several times more than the aim (falloff with distance), so Dramatic now stands further out and higher with softer falloff, and Raking from the top has falloff 0.25. Warm evening cooler and lower, Candlelight lifted (less muddy), Soft window a touch warmer. Near-white share (luma >= 235) for Dramatic: door 6.4% to 0.5%, lintel 10.8% to 1.8% (photo 0.07% / 1.8%). Round 3 published.
- **D-022. Round 3 (Isaac): "overall good"; raking shows too little shadow, wants a few strengths of cast shadow.** Shadows need Texture (relief, Phase 4: §5.3 `sh`, §5.6); the Light layer has none to give, so the looks stay as they are. Phase 4's review round shows both raking looks with Texture on at several Shadows values (for example 0.3, 0.6, 1) and Depths, so he can pick the strengths.
- **D-023 (Phase 2). Preview choices.** `gl` takes the lamps from core's `prepareLighting(doc, a, 1)` (no lighting maths duplicated in TypeScript) and `kappa` as its own uniform (`E *= kappa`, the same as folding it in). The transfer curve is the exact piecewise sRGB formula in the shader (§10 allows it): a filtered texture sample is not a whole code, so a table lookup would not fit. The parity test gives the preview the photo at 1024 px, resized by core (area average), and compares the lighting; how the GPU filters a zoomed-out view (mipmaps on the 8-bit values) is a display matter and not compared. Measured on the lintel: every channel within 1 level on all six documents, neutral exact. Outside the picture the canvas is transparent (Phase 3 draws the margin). A reduced scale `q` draws into a smaller framebuffer and blits it up.
- **D-024. `e2e` is a workspace package** (`e2e/`, as §4) with `@playwright/test` pinned to 1.63.0, the version preinstalled in cloud sessions (so it finds `/opt/pw-browsers`), and `vite` to serve the harness page. Chromium runs with SwiftShader (`--use-angle=swiftshader --enable-unsafe-swiftshader`). Run with `pnpm e2e`; CI runs it as a second job that installs Chromium (on GitHub's machines, not in cloud sessions) without `--with-deps`: the runners already have its libraries, and the apt step failed when Ubuntu's mirrors did not resolve. `core` now also exports `prepareLighting` and `thumbnail`.
- **D-025 (Phase 3). The app's moving parts.** `@preact/signals` added (D-002). While a handle, slider or wheel is held the picture shows an uncommitted document (`preview`); letting go commits it through `commands` as one undo step. The guard (§5.7) runs in its own worker on the 512 px thumbnail (it is its own guard thumbnail, so the factor is exactly `guardKappa(photo, doc)`): a release draws at once with the last factor and the new one follows (about 180 ms on the main thread when the guard engages would break the 150 ms release budget). Adaptive scale: §9's rule, plus 30 frames in a row at the display's rate count as room to raise (a 60 Hz display never shows a frame under 12 ms). The page is cross-origin isolated (`public/_headers`, Vite's dev and preview headers) so the render workers share one copy of the photo; without isolation one worker gets a copy.
- **D-026. Export lives in `web`, not `core`** (core has no image encoding). `window.digilight.export({width, format, quality, download?})` returns the file and its record: the document, the photo file's SHA-256, and the picture's SHA-256 twice, of its RGBA pixels (`pixelsSha256`, equal to the reference renderer's in Node) and of the encoded file. `window.digilight.open` also takes a File, Blob or URL. Sizes larger than the photo are not offered (no upscaling on export).
- **D-027. Simple sliders show 0 to 100 (Brightness and Room light as %)** mapped as §6 says; a value set outside a simple mapping (for example cone 5 from expert) shows at the slider's end and is kept until the slider is moved. A sun has no place on the picture: its handle sits on a ring round the centre toward where it shines from, and dragging it sets the sun's direction. Expert lists hide settings that mean nothing for the light's kind (azimuth and elevation for a lamp; cone, edge, falloff for a sun). Tone settings are listed under Lights. Handles past the canvas edge are drawn at the edge. Pinch on a handle (touch) zooms instead of changing brightness; a trackpad pinch over a handle zooms too.
- **D-028. Zoom to 800% means 8 screen pixels per photo pixel**, the most useful reading for a 24-megapixel photo (8 times the fit would still be under 1:1).
- **D-029. The smoke test opens a PNG** made from `door-flat-crop.jpg` at 1200 px (`e2e/png.ts`, Node zlib), so the browser decodes exactly the pixels the Node reference renders (JPEG decoders differ by a level here and there). It checks the record's pixel SHA-256 against the reference and that the PNG file decodes to those pixels.
- **D-030. Export on a phone goes to the share sheet** (Isaac, after trying it on his iPhone: Safari's download left him unsure where the picture went). Where the browser can share files (`navigator.canShare`), a finished export shows **Save or share** in the top bar ("Save Image" there puts it in Photos), with Download beside it; no automatic download, and the `.json` record only comes with Download. The share must start from a tap, and an export takes longer than the browser counts a tap as fresh, so it is a second tap. Elsewhere (the iMac) the picture and record download as before.
- **D-031. Opening a big photo, faster.** Bench on Isaac's iMac (17.9 MP): open 1.16 s against 1.5 s, so at 24 MP it would be at the limit. The file's SHA-256 now runs while the photo decodes, and the guard worker makes its 512 px thumbnail from the shared photo itself (the main thread made it before). The bench's JavaScript row reads each script's compressed size (`encodedBodySize`); the transferred size is near 0 when the browser has the files cached (it read 2 KB).
- **D-032. Isaac's notes after Phase 3 (11-12).** Looks: Gallery, Spotlight and Dramatic too warm (lamps 3600 to 3800 K, room light 5000 K); Candlelight too blown out (a lamp close below the bottom edge). Tuning is the first step of Phase 4, then a review round. New tools go in Phase 6 (BUILD.md items 6 and 7): Zoom out, Fit, Zoom in buttons, and a Settings window from Export with saved presets, copy and paste of settings onto other photos, and projects.
- **D-033 (Phase 4). Looks retuned from Isaac's notes after Phase 3 (D-032).** Gallery, Spotlight and Dramatic: room light 5000 to 6000 K, lamps 3600 to 3800 K to 4500 to 4600 K (red to blue ratio against the photo: gallery 1.24 to 1.11, spotlight 1.33 to 1.14, dramatic 1.33 to 1.17). Candlelight's lamp stands further below and higher, with less falloff ((0.5, 1.2, 0.5), falloff 0.8 to (0.5, 1.5, 0.6), 0.6; 2600 to 2700 K, aim 0.65 to 0.6): no hot spot at the bottom edge. `kappa` stays 1 on the door and lintel for all four. BUILD.md §6 table and goldens updated. Review round 4 asks him to confirm.
- **D-034. Estimate details §10 leaves open.** Chroma divides by `max(luma, 0.002)` (black pixels). A Gaussian of sigma over 3 pixels (D-039; was 5) is three box blurs of matching variance (within 1%; the 0.012-width blurs at 2048 px are 25 pixels); up to 3, the exact kernel to 3 sigma. Percentiles from an evenly strided sample of at most 2^20 values. A photo whose 2% to 98% spread is under 1e-6 (one colour) gets `hHat = 0`. New files for one job each: `core/relief/blur.ts`, `relief/sample.ts` (reading the maps), `relief/index.ts`; `gl/shaders/horizon.glsl.ts`; `web/relief.ts` (making the maps across workers) and `panel/Texture.tsx`.
- **D-035. Horizon taps at whole-pixel offsets, divided by the offset's own length.** `floor(0.5 + t_j d_k / texel)`: the CPU and GPU read exactly the same texels (the GPU table matches the CPU's within 1 byte on every entry). Dividing by `t_j` instead overstated the rise by up to 41% on diagonals (offset (1, 1) for t = 1). §5.6 updated. CPU speed: Tmax first, taps in order, a tap skipped once a bound (block max minus block min round the pixel's block, from a max and a min pyramid) cannot beat the best so far; then each layer as plain row walks. Door at 1805 px on this cloud machine, one thread: estimate 1.0 s, Tmax 3.4 s, table 9.3 s; the app splits Tmax and layers by direction across the workers (§10).
- **D-036. The max pyramid overstates rises on even slopes** (up to 35%: a block's max sits at its far side). Against an exact ray march on a smooth ridge, pit and ramp (default Softness 0.05), mean `|vis|` error is under 0.03 from 10° up, but 0.02 to 0.08 at 3° and 5° (0.008 to 0.028 with plain taps and no pyramid). §5.6 kept as written (the pyramid keeps thin ridges from being stepped over); the test holds 0.03 from 10° and 0.08 below. Revisit if low raking shadows look too long.
- **D-037. Texture in the render.** With relief on, suns are per-pixel lights (rel and sh vary); without, they stay folded into the constant. Sheen gets the same per-channel factor as E (white adapt, `kappa`). The relief maps are sampled with picture coordinates (`x * Wr - 0.5`, clamped), the same in the shader (linear filtering) as in the reference. `ao` is made from the table's bytes. `prepareLighting(doc, a, kappa, maps | true | null)`: `true` means relief on with the maps on the GPU. A Light-layer render is unchanged bit for bit (goldens).
- **D-038. How the app makes the maps.** Texture switched on: a worker estimates the height and builds the pyramid (shared memory when isolated), the workers split Tmax by direction, then the table is made twice at once: on the GPU for the picture (two directions a frame; the picture shows the Light layer until it is ready, with "Preparing the texture…") and by the workers for exports, which wait for it. Look thumbnails stay Light layer only. `setRelief` is the command (D-015); switched on with Depth and Shadows never set, they start at 0.003 and 0.4 (`RELIEF_START`). `measured` is refused until Phase 5.
- **D-039. Texture on, faster (bench: 3.55 s at 3.8 MP, 3.9 s at 17.9 MP, against 3 s).** On this cloud machine the old path was estimate 1.27 s, pyramid 0.61 s, then Tmax 1.65 s on 3 workers before the GPU could start. Now: (1) the GPU finds Tmax itself (per-pixel max over the directions, two a frame, then a 4 x 4 max reduction and one float read; needs `EXT_color_buffer_float`, else it waits for the workers' Tmax), within 1e-7 of the CPU's; the workers still find their own for exports. (2) The estimate runs in stages across the workers (rows of the resize to relief size, rows of the channels, one blur each, rows of the raw height), the same bits as in one go (tested). (3) The 0.002-width blur of `hs` is three boxes (sigma over 3 pixels), the exact kernel reads rows straight through: pyramid 0.61 to 0.32 s. Expected on the iMac about 2 s; the bench now also shows the estimate's share. The bench's JavaScript row counts each script once (three render workers load the same file; 272 KB was that file counted three times; each ships once: about 171 KB).
- **D-040 (Phase 5, engine). The port.** v1 `lampphotos.js` is `relief/measure.ts` with its parts in files of one job each (under 300 lines): `box.ts` (v1's box blur and percentiles), `align.ts`, `shading.ts`, `integrate.ts`; v1 `lineup.js` is `lineup.ts` with `features.ts`. `Math.*` became `dmath`; the sRGB decode is core's table; `measureRelief` is synchronous with `onProgress` (it runs in a worker or in Node). v1's sun and lamp constants were equal, so there is one of each. Against v1 run in Node on the same photos: heights equal within 0.00005 px on the door, the lintel and the three-lamp piece (correlation 1.000000; lamp checks 0.869 / 0.864 / 0.798 as v1), the line-up within 0.002 px on both handheld photos. A 2.3 MP measurement takes about 10 s in Node (v1: 13 to 17 s), a line-up about 9 s.
- **D-041. The light's axis: band 1 to 8 px (at 1280 wide), each gradient counted for at most the 75th percentile's size.** azimuth.py's version (2 to 12 px, plain) read 153.5 for the door's 135 and 158.6 after the app's own line-up (23.6 off, over the 20 allowed): a few hard edges along the picture's own axes pulled it. Now, on the five pairs: door 143.4, lintel 34.7, lamps 93.3 / 129.7 / 47.7 (worst 12.3 off); with the app's own line-up, door 147.6, lintel 34.3.
- **D-042. The measured height is kept as 16 bits a pixel** (`MeasuredHeight`: hHat between `lo` and `hi`; `packHeight` puts the high byte in red and the low byte in green for a PNG), and the maps are always made from those 16 bits, so a reopened project gives the same pixels. hHat's spread is the measurement's 2% to 98% spread away from the edges (v1's depth), its median over the whole picture; `relief.depth` starts at that spread in picture widths (at most 0.03). With one sun-like photo, light from the other end gives exactly the height turned over (tested), so `flipped()` answers "the other end" without measuring again.
- **D-043. Commands.** `measureRelief({photos: [{image, from?, elevation?, lamp?}], widthCm?})` takes decoded photos in core (the app's `window.digilight` will take `src`, as `open` does). No `from`: the axis read from the pair, its upper end, and `assumedEnd: true` in the answer (the other end is + 180). A photo is treated as sunlight from (`from`, `elevation`, default 20); `lamp` in cm (v1's way) needs a tripod shot of the photo's own shape and the width in cm, and is aligned, not lined up by homography. `setMeasured(height, depth?)` and `getMeasured()` carry the height for the app's worker and for project files; `setRelief({mode: 'measured'})` works once there is one. The height sits beside the document: undo brings back the document, not an earlier height.
- **D-044. The gate as a script: `pnpm gate:relief`** (`bench/relief-gate.ts`, about 3 minutes; a CI job). The handheld sun photos are lined up by the app's own code; the "sun-like light" is a document (room light 0.1, one sun at the documented direction, brightness 1, softness 0.01, Shadows 1, measured Depth) rendered by the reference and scored by `bench/relief-score.ts` against the real photo. Shade corr mid / broad: door 0.78 / 0.87, lintel 0.68 / 0.85 (needs 0.45 / 0.50; v1 0.55 / 0.60 and 0.54 / 0.51). With the app's own axis, 20 degrees assumed and the right end, still relit from the documented direction (the stricter reading): door 0.79 / 0.88, lintel 0.59 / 0.78 (needs 0.40 / 0.45). DSC_8382: 0.87, 0.86, 0.80 (needs 0.7). `relief-score.ts` leaves out score.py's warmth column (not about relief). The root `package.json` is `"type": "module"` so Node runs `bench/*.ts` without a warning.

- **D-048 (Phase 5, app flow).** The side-lit photos go to their own worker (`measure.worker.ts`), so a 10 to 15 s job never holds the render workers; it is loaded only when the flow starts (59 KB gzip; the page's first load is unchanged). Each photo is lined up once at relief size; the previews are one measurement at long side 512 from those lined-up pixels resized, and the same height turned over (`flipped`). Preview A takes each photo's light from its axis's upper end (as core's command does with no `from`), B from the other ends; both are lit from photo 1's axis end nearer the upper left (135°), at 25° with Shadows 1. The Texture switch uses the measured height once there is one. The maps come from the 16 bits (`relief-height` takes `measured`; no blur for the table, as core's `measuredRelief`), so exports equal Node's render. Autosave keeps the height as a PNG in IndexedDB with `lo` and `hi`; reopened, the document is set first and then the height, so it adds no undo step. `window.digilight.measureRelief({photos: [{src, from?, elevation?, lamp?}], widthCm?})` runs the same worker without the previews; `getMeasured()` gives the height and how it was measured.
